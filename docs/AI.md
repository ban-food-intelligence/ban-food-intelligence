# AI studies (spec section 4)

Two mandatory models, both compared with a simple reference method and measured on data the
model has not seen. Lot traceability and recall **never** use these predictions; they come only
from recorded lot relations (`lot_link`, `shipment_line`, `sale_line`) in MySQL.

| Study | Predicts | Inputs | Champion model | Baseline |
|---|---|---|---|---|
| A, production | packages received (`actual_qty`) and unit cost (EKP) of an external production order | product, subcontractor, meat supplier, meat/spice/casing kg, meat fat %, meat age, drying days, season, planned qty | Ridge regression (one-hot + scaling) | historical mean yield of the product |
| B, butchery | weight of each part (leg, loin, shoulder, ribs, mince) and waste | species, breed, carcass weight, age, sex, fat and conformation score, chill hours, operator, supplier | Ridge regression on part shares, normalised to 100 % | historical mean part shares of the species |

## Data

- Real history does not exist for the competition, so `ml-engine/generator_ali.py` creates a
  **synthetic, anonymised** history (Jan 2024 to Sep 2026; 1,500 production orders, 2,500
  butchery operations) from a documented process model anchored on the spec numbers
  (100 kg meat + 2 kg spice + 5 kg casing -> 85 packages; lamb 25 kg -> 22 kg parts + 3 kg waste).
  The generator is seeded, so the files are reproducible.
- The same columns are exposed from the real database by the views `v_ml_production_features`
  and `v_ml_butchery_features`, so the models can be retrained on real records without code changes.

## Method

- **Production:** the model predicts the yield %; packages and EKP are then calculated with the
  exact cost formula (EKP = (material cost + packages x service price) / packages). The cost side
  therefore always matches the accounting; only the yield is learned.
- **Butchery:** six shares are predicted and normalised to 100 %, so predicted parts + waste
  always equal the input weight (mass balance holds by construction).
- **Validation:** time split. Rows are sorted by date; the latest 20 % of dates are the test
  period. The champion is chosen by 5-fold cross-validation on the training period only. A random
  split was rejected because price columns rise with inflation and act as a hidden time signal.
- CatBoost was also trained; Ridge is the champion (equal accuracy, simpler and explainable).

## Results on the held-out test period

Generated by `ml-engine/export_ai_report.py` into the `ml_model_metric` table and served by
`GET /ai/summary`.

| Study | Target | Model MAE | Model MAPE | Baseline (hist. mean) MAE | Baseline MAPE | Recipe baseline MAPE |
|---|---|---|---|---|---|---|
| A | packages (302 orders) | 1.37 packages | **1.18 %** | 2.69 packages | 2.24 % | 2.85 % |
| A | EKP | 0.138 EUR | **0.81 %** | 0.259 EUR | 1.54 % | 1.90 % |
| B | part weight (500 operations) | 0.115 kg | **3.27 %** | 0.170 kg | 4.79 % | 4.81 % |
| B | waste weight | 0.113 kg | **4.40 %** | 0.251 kg | 9.81 % | 10.03 % |

The model roughly halves the error of the simple reference method on every target.

## Predictions on the demo records

`GET /ai/summary` shows, for the seeded records, the model prediction, the baseline prediction,
the actual value and the deviation (absolute and %):

| Record | Target | Actual | Model | Model dev. | Baseline | Baseline dev. |
|---|---|---|---|---|---|---|
| URT-2026-045 | packages | 85 | 84.6 | 0.47 % | 83.35 | 1.94 % |
| URT-2026-045 | EKP | 18.16 EUR | 18.22 EUR | -0.32 % | 18.41 EUR | -1.38 % |
| URT-2026-046 | packages | 83 | 82.8 | 0.24 % | 83.35 | -0.42 % |
| PRC-2026-001 | leg | 6.50 kg | 6.79 kg | -4.52 % | 6.56 kg | -0.91 % |
| PRC-2026-001 | waste | 3.00 kg | 2.61 kg | 13.1 % | 2.92 kg | 2.55 % |

On the single butchery demo record the baseline is closer for four of six parts. That record was
written by hand to match the standard lamb recipe split (26/14/20/12/16/12 %), which is almost
exactly the baseline. One record proves nothing either way; the 500-operation test period above
is the measurement.

## Limitations

- The training data is synthetic. The results show how well the process can be learned, not how
  the model performs in a real plant. They must be re-measured once real orders accumulate.
- Few real records exist (2 production orders, 1 posted butchery operation), so deviations on the
  demo records are anecdotes, not accuracy.
- The models do not know about events that are not in the features (machine failures,
  mislabelled lots). Large deviations are flagged by the anomaly detector (`anomaly_ali.py`) for a
  human to check; they never change stock, cost or lot status.

## Why traceability never uses AI

Recall decisions must be exact and auditable: which lots, which customers, how many packages.
They are answered by recursive SQL over recorded relations (`sp_trace_forward`,
`sp_trace_backward`, `sp_recall_initiate`). A prediction can be wrong; a recorded shipment cannot
be "probably" at Market B. The AI features only estimate yields and costs to support planning and
to flag unusual results.

## Reproduce

```bash
pip install -r ml-engine/requirements.txt
python ml-engine/generator_ali.py      # synthetic history (seeded)
python ml-engine/train_model_ali.py    # time-split training + metrics.json
python ml-engine/export_ai_report.py   # writes the AI block of database-mysql/seed.sql
pytest ml-engine/tests -q
```
